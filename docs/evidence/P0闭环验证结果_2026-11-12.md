## 关键修复（Vulkan B 帧挂死）

早期 Vulkan 后端在第 4 帧左右出现 VCN ring timeout / mode1 reset。根因是绑定到
`VkVideoSessionKHR` 的 `VkDeviceMemory` 在 bind 成功后就被 `vkFreeMemory`，违反 Vulkan
“必须存活到 session 销毁”的要求；后续分配复用了这块固件上下文内存。根因、修复清单和
测量陷阱见 [Vulkan 后端实现 §8](../architecture/Vulkan后端实现.md#8-上机验证结论rx-7900-xtx--radv)。

同批修复还包括：

- SPS/PPS 缓存改存 `nal.raw_data`（保留 EPB），避免重新切分时 `00 00 01` 被误判为 start code；
- 多平面导出按 plane texel 单位计算 `imageExtent` / `bufferRowLength` / `bufferImageHeight`；
- DPB 槽位改为升序分配，避免越过 `ref_frame_list[]` / 槽位掩码范围；
- barrier 覆盖 setup 槽和全部参考槽；
- 解码状态 query、fence 超时和 `CUVID_SHIM_DEBUG_VK` 诊断开关。

> 早期文档里“VAAPI 输出平坦 0x80 / 色度 PSNR ≈ 6 dB”是**测量方法错误**（把 pitch 跨行的
> NV12 当 planar 比较），VAAPI 后端同样逐帧位精确；详见 [Vulkan 后端实现 §8.4](../architecture/Vulkan后端实现.md#84-测量陷阱重要教训)。

## 复现命令

```bash
# 验证机脚本统一显式设置 RADV_PERFTEST=video_decode
RADV_PERFTEST=video_decode CUVID_SHIM_BACKEND=vk \
  LD_LIBRARY_PATH=cuda_shim:$HOME/ffmpeg-7.1/libavutil \
  ./cuda_shim/verify_kernel_read testdata/h264/test_p_b_5.h264
```

更完整的 dump/比对命令见
[Vulkan 后端实现 §7](../architecture/Vulkan后端实现.md#7-验证入口) 和
[验证手册 §3.5](../verification/验证手册.md#35-画面正确性-dump-对比)：

```bash
RADV_PERFTEST=video_decode CUVID_SHIM_BACKEND=vk \
  CUVID_DUMP_NV12_DIR=/tmp/vkd \
  ./cuda_shim/verify_kernel_read testdata/h264/test_p_b_5.h264
```

`verify_kernel_read` 的 `OK/Ysum/UVsum` 只证明 kernel 读到的和 CPU 读到的是同一块内存，
**不校验画面**；画面正确性要用 `CUVID_DUMP_NV12_DIR` dump 后与软解参考逐帧逐平面比较
（注意 pitch 跨行 + NV12 交织）。

## 能证明什么

- VAAPI 与 Vulkan Video 两条数据通路都能完成真实解码、显存导出/导入和 HIP 读取。
- 四路码流在两个后端上都与软件参考逐字节一致，覆盖 I/P/B、不同 profile 和无 B 帧对照组。
- `verify_kernel_read` 通过，说明 map 返回的 `dev_ptr` 能被 HIP kernel 直接按 pitch 寻址，
  并且 `hipEventSynchronize` 后再 unmap 的顺序正确。
- libcuda 符号面、功能子集、CUVID parser 与会话创建均通过。

## 不能证明什么

- 尚未证明 FFmpeg `h264_nvdec` 宿主路径的零拷贝验收（本次结果未包含该组合）。
- 尚未覆盖多流、seek/flush、动态分辨率、P010/奇数分辨率。
- 尚未覆盖自研目标平台、1/8 路 30 分钟稳定性、真实业务性能。
- `verify_kernel_read` 的 checksum 只证明“kernel 可寻址 + event 顺序”，
  不独立证明解码像素正确；像素正确性由上面的四路码流表格证明。

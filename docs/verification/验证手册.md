> 版本：v1.1

## 2. 构建

### 2.1 兼容层与组件测试

```bash
cd cuda_shim

make -j"$(nproc)" libcuda.so.1 libnvcuvid.so.1 test_func_full \
  ROCM_DIR=/opt/rocm \
  FFMPEG_DIR=$HOME/ffmpeg-7.1 \
  NVCODEC_DIR=$HOME/nv-codec-headers/include \
  MESA_DIR=$HOME/mesa \
  VULKAN_LIB=-l:libvulkan.so.1
```

说明：

- `VULKAN_LIB=-l:libvulkan.so.1` 用于只有运行时 `libvulkan.so.1`、没有 `libvulkan.so` 开发软链的机器；装了 `libvulkan-dev` 可省略。
- 某些 ROCm clang 找不到系统 libstdc++ 时（报 `Could not find standard C++ header 'cmath'`）：

```bash
make verify_kernel_read \
  ROCM_DIR=/opt/rocm \
  HIPCC_EXTRA="-I/usr/include/c++/11 -I/usr/include/x86_64-linux-gnu/c++/11 -L/usr/lib/gcc/x86_64-linux-gnu/11"
```

- 验证机是 RX 7900 XTX（gfx1100）时，显式指定目标架构：

```bash
make verify_kernel_read ROCM_DIR=/opt/rocm HIPCC_EXTRA="--offload-arch=gfx1100"
```

两种 `HIPCC_EXTRA` 可合并；`--offload-arch` 按 `rocminfo | grep gfx` 调整。`verify_kernel_read` 必须用 `hipcc`（设备端 kernel），没有放进 `make all`。

## 3. 快速验证

### 3.1 确认 FFmpeg 的两类入口

```bash
ffmpeg -hide_banner -decoders | grep 'h264_cuvid'
ffmpeg -hide_banner -hwaccels
```

必须明确：

- `h264_cuvid` 是 **decoder**，可以通过 `-decoders` 查到。
- FFmpeg 7.1 的 `h264_nvdec` 是 **hwaccel**，不会出现在 `-decoders` 列表。正确调用是
  `-hwaccel nvdec -hwaccel_output_format cuda`，不是 `-c:v h264_nvdec`。
- 找不到 `h264_cuvid` 或运行时无法使用 NVDEC，说明当前可执行文件/库组合不对，必须先修正构建与加载路径，不能跳过。

### 3.2 mapped dev_ptr 的 kernel 可访问性 + event 顺序

```bash
cd cuda_shim
export LD_LIBRARY_PATH=$PWD:$HOME/ffmpeg-7.1/libavutil:${LD_LIBRARY_PATH:-}

./verify_kernel_read ../testdata/h264/test_p_b.h264
CUVID_SHIM_BACKEND=vk ./verify_kernel_read ../testdata/h264/test_p_b.h264
```

或一次跑两个后端：

```bash
../tests/quick-verify/run_kernel_read.sh
```

预期：每帧 `Ysum/UVsum ... OK`，最后 `PASS: mapped dev_ptr is kernel-addressable ...`。VK 后端在缺少 Vulkan Video 解码时会明确失败；可先 `BACKENDS=vaapi ./tests/quick-verify/run_kernel_read.sh`。

> `OK/Ysum/UVsum` 只证明 GPU kernel 与 CPU 读到同一块 mapped 显存，**不校验画面内容**。画面正确性见 §3.4 和实验 C。

### 3.3 FFmpeg 宿主双后端矩阵（像素、显示顺序、零拷贝、资源）

```bash
cd /path/to/repo

# 完整矩阵：四路码流 × VAAPI/VK × 四种宿主模式
FFMPEG=$HOME/ffmpeg-7.1/ffmpeg \
  ./tests/quick-verify/run_ffmpeg_compare.sh

# 只跑一个后端或部分模式（用于定位，不代替完整矩阵）
BACKENDS=vaapi MODES="nvdec-safe cuvid-cpu" \
  FFMPEG=$HOME/ffmpeg-7.1/ffmpeg \
  ./tests/quick-verify/run_ffmpeg_compare.sh

# 归档证据；目录必须为空，不归档 YUV
FFMPEG=$HOME/ffmpeg-7.1/ffmpeg \
  EVIDENCE_DIR=docs/evidence/ffmpeg-host-$(date +%F) \
  ./tests/quick-verify/run_ffmpeg_compare.sh

# 保留临时中间文件排查
KEEP=1 FFMPEG=$HOME/ffmpeg-7.1/ffmpeg \
  ./tests/quick-verify/run_ffmpeg_compare.sh
```

脚本固定加载 `FFMPEG_BUILD_DIR`（默认从可执行文件所在目录或 `$HOME/ffmpeg-7.1` 探测）中的 FFmpeg 库，并用 `ldd` 验证 `libavcodec` 确实来自该构建树，避免误加载 `/usr/local/lib` 或系统另一套库。

矩阵覆盖四种模式：

| 模式 | 入口 | 预期与判据 |
|---|---|---|
| `nvdec-safe` | `-hwaccel nvdec -hwaccel_output_format cuda` + `hwdownload` | 像素必须一致；记录 D2D，**不能作为零拷贝证据** |
| `nvdec-unsafe` | 上一行加 `-hwaccel_flags unsafe_output -extra_hw_frames 16` | 像素一致且 D2D=0，才可作为 NVDEC 零拷贝候选证据；额外 surface 用于下游/线程持有帧 |
| `cuvid-cpu` | `-c:v h264_cuvid`，直接输出 NV12 | 像素必须一致；CPU 回读不计入 D2D |
| `cuvid-cuda` | `-c:v h264_cuvid -hwaccel cuda -hwaccel_output_format cuda` + `hwdownload` | 像素必须一致；记录 FFmpeg 自身逐平面 D2D |

每个组合必须同时通过：退出码、帧数、输出大小、逐字节像素、D2D 计数。输入含 PTS 时还比较完整 PTS 序列；P0 裸 Annex-B 码流没有输入 PTS，报告记 `NA(no-input-pts)`，此时逐帧像素一致就是显示顺序证据。脚本还采样 `/proc/<pid>/fd` 和 `VmRSS` 的首值、末值、峰值；这只能记录短时资源行为，不是长稳泄漏结论。

**禁止 SKIP：** 缺少必需 decoder、NVDEC 不可用、后端失败或组合无法执行都必须 FAIL。全部未执行时退出码非 0。

2026-11-13 修复后完整矩阵：**32 RUN / 32 PASS / 0 FAIL / 0 SKIP**。

| 后端 | `nvdec-safe` | `nvdec-unsafe` | `cuvid-cpu` | `cuvid-cuda` |
|---|---|---|---|---|
| VAAPI | 4/4 PASS | 4/4 PASS，D2D=0 | 4/4 PASS | 4/4 PASS |
| Vulkan | 4/4 PASS | 4/4 PASS，D2D=0 | 4/4 PASS | 4/4 PASS |

`nvdec-unsafe` 使用 `-extra_hw_frames 16`。FFmpeg 的 NVDEC frame pool 默认只按 SPS 参考帧数加少量余量分配；零拷贝输出被下游和线程持有后，默认池会出现 `No decoder surfaces left`。shim 的 surface 上限已从 32 放宽到 64，宿主可分配足够 surface。Vulkan `h264_nvdec` 不经过 shim parser，后端现在会从 `CUVIDH264PICPARAMS` 合成最小 SPS/PPS 来建立会话。

完整日志、命令、环境和摘要见 [FFmpeg 宿主双后端基线](../evidence/FFmpeg宿主双后端基线_2026-11-13/README.md)。

严格 PTS 分支使用带时间戳的小体积 MP4：

```bash
BACKENDS=vaapi STREAMS=test_pts_320x240.mp4 \
  FFMPEG=$HOME/ffmpeg-7.1/ffmpeg \
  EVIDENCE_DIR=docs/evidence/ffmpeg-pts-$(date +%F) \
  ./tests/quick-verify/run_ffmpeg_compare.sh
```

2026-11-13 修复后结果：VAAPI + Vulkan 共 8 组合 **8 PASS / 0 FAIL**，所有模式（含 `nvdec-unsafe` 零拷贝）的 PTS 与软件参考严格一致。详见 [PTS 顺序验证](../evidence/FFmpeg_PTS顺序_2026-11-13/README.md)。

### 3.4 零拷贝计数器自检（可选）

```bash
cd cuda_shim
CUDA_SHIM_TRACE_COPY=1 ./test_func_full 2>&1 | grep copy-trace
```

`test_func_full` 里有一次 D2D `cuMemcpy2DAsync`，应看到 `D2D=1` 左右；一行都没有说明环境变量没生效或进程未正常退出。

### 3.5 画面正确性 dump 对比

```bash
cd cuda_shim
LD_LIBRARY_PATH=. CUVID_SHIM_BACKEND=vk RADV_PERFTEST=video_decode \
  CUVID_DUMP_NV12_DIR=/tmp/vkd ./verify_kernel_read ../testdata/h264/test_p_b_5.h264

LD_LIBRARY_PATH=. CUVID_SHIM_BACKEND=vaapi \
  CUVID_DUMP_NV12_DIR=/tmp/vad ./verify_kernel_read ../testdata/h264/test_p_b_5.h264

ffmpeg -v error -y -i ../testdata/h264/test_p_b_5.h264 -f rawvideo -pix_fmt yuv420p /tmp/ref.yuv
```

逐帧逐平面比较时注意：dump 是 **pitch 跨行的 NV12**（亮度 `y*pitch`，色度从 `pitch*H + y*pitch` 开始，U/V 交织）；参考是 planar yuv420p，需要先交织或分别比 `dump[0::2]==U`、`dump[1::2]==V`。

### 4.2 实验 A：parser 复用

```bash
cd tests/parser
make -f verify_parser_reuse.make
./verify_parser_reuse ../../testdata/h264/test_320x240.h264
```

结论：

- 原始 8 个 `.o`（`h2645_parse` / `h264_ps` / `h2645_vui` / `h2645data` / `h264data` / `golomb` / `mathtables` / `refstruct`）可静态链接，不拖入编解码器依赖。
- 当前构建在此外加 `h264_parse.o`，共 9 个，用于 `ff_h264_init_poc` / `ff_h264_parse_ref_count`。
- 这些源文件均为 LGPL；干净构建（`CONFIG_GPL=0` / `CONFIG_NONFREE=0` / `CONFIG_PIC=1`）下可生成并重链接。
- SPS/PPS 从 `sps_list[]` / `pps_list[]` 取（非 `ps.sps/ps.pps`）；PPS 字段名 `cabac` / `deblocking_filter_parameters_present` 已规避踩坑。
- 编译 FFmpeg 内部头需 `#define HAVE_AV_CONFIG_H 1`，否则 `golomb.h` 的 `SUINT` 未定义。

### 4.3 实验 B：LGPL 干净构建

```bash
cd tests/parser
./run_lgpl_build_check.sh
```

判据：干净构建下任一 `.o` 缺失或重链接失败 → 分发路线需改。

### 4.4 实验 C：真实解码 → HIP 读

判据：多帧各 plane 逐字节一致 + 无 fd/内存泄漏 + 无非法访问。当前结果见 [P0 闭环验证结果](../evidence/P0闭环验证结果_2026-11-12.md)。

实验 C 已知坑（已修复，保留用于回归）：

1. **`log2_max_pic_order_cnt_lsb_minus4` 少减 4**：FFmpeg 的 `sps->log2_max_poc_lsb` 是完整位数，VAAPI 字段名含 minus4 但硬件按 `值+4` 解读；直接传完整值会让 slice 数据整体错位 4 bit，连 IDR 都错。应传 `sps->log2_max_poc_lsb - 4`。
2. **DPB 滑动窗口误删参考帧**：滑动窗口只在 `nal_ref_idc != 0` 时执行；旧代码对非参考 B 帧也执行，导致参考帧被误删。
3. **VAAPI `VAPictureParameterBufferH264` 字段**：补填 `frame_num`、`pic_order_present_flag`、`reference_pic_flag`。
4. **`h264_vaapi` 编码器在 `bframes=0` 时强制 `poc_type=2`**：带 P 帧的测试码流用 VAAPI 生成时是 `poc_type=2`，代码需支持 `0/2` 双路径。
5. **无 libx264 时**：AMD 机可能没有 libx264，`-preset` 会报错；改用 `h264_vaapi -profile:v 77` 生成 Main profile 码流。
6. **未覆盖**：`poc_type==1`（delta POC 全字段）、场编码、加权预测、SP/SI；遇到时显式返回不支持。

## 5. 常见问题

| 现象 | 处理 |
|---|---|
| `Cannot load libnvcuvid.so.1` | `LD_LIBRARY_PATH` 把 `cuda_shim` 放在系统路径前；`ls -l libnvcuvid.so.1` 确认 soname |
| `verify_kernel_read` 在 `cuvidCreateDecoder` 失败 | VK 后端先看 `vulkaninfo \| grep -i video`；VAAPI 先看 `vainfo` |
| `hipcc` 报找不到 `cmath` / `cstdlib` | 加 `HIPCC_EXTRA`（见 §2.1） |
| `cannot find -lvulkan` | `sudo apt install libvulkan-dev`，或 `VULKAN_LIB=-l:libvulkan.so.1` |
| `ff_h2645_packet_split` 参数数量错 | 用了 FFmpeg 6.1；换 7.1 或改回 6.1 签名 |
| `ff_h264_init_poc` undefined | 缺 `h264_parse.o`；确认 9 个 `.o` 都在 |
| `vulkaninfo` 无 video 队列 | 检查 Mesa/RADV 版本；验证机脚本显式设置 `RADV_PERFTEST=video_decode` |
| FFmpeg 输出与软解不一致 | `KEEP=1` 保留 raw 文件，`cmp -l` 看首个差异；确认是否走了 `h264_cuvid`（会多一次 D2D） |
| 没有 `copy-trace` 行 | 确认 `CUDA_SHIM_TRACE_COPY=1` 且 FFmpeg 正常退出 |
| `verify_cuvid_session` 在 VK 后端“session 未建” | 该程序只建 decoder 不喂流，SPS/PPS 未到，属预期 |

## 6. 结果记录与证据规范

记录原始证据，不要只写“通过”：

```text
verify_kernel_read vaapi: frames_ok=30 errors=0 PASS
verify_kernel_read vk   : frames_ok=30 errors=0 PASS
run_ffmpeg_compare      : 32 RUN / 32 PASS / 0 FAIL / 0 SKIP
  vaapi/nvdec-safe  : 4/4 pixel-identical, D2D>0 (FFmpeg safe path)
  vaapi/nvdec-unsafe: 4/4 pixel-identical, D2D=0
  vk/nvdec-*        : 8/8 pixel-identical, unsafe D2D=0
  */cuvid-*         : 16/16 pixel-identical
```

归档时保留 `summary.tsv`、`summary.md`、`environment.log`、`commands.log` 和每个组合的原始日志/PTS；不要提交中间 YUV。

失败时优先保留：

- `KEEP=1` 的 `WORK` 目录；
- FFmpeg stderr；
- `verify_kernel_read` 完整输出；
- `dmesg`（VCN timeout / GPU reset 时）。

原始日志、命令和环境版本放入 `docs/evidence/`；不要把“程序跑过”当成“像素正确”。

## 7. 已知限制

- 本手册覆盖底层数据通路、shim 路径与验证流程；**不覆盖**多流、seek/flush、P010/奇数分辨率、动态分辨率、NPP 联合链路、异步 fence、1/8 路 30 分钟稳定性。
- `verify_kernel_read` 逐帧做 GPU checksum + CPU 回读，适合正确性，不适合性能结论。
- FFmpeg 宿主双路径已在当前四路 320×240 码流上 32/32 通过，包括双后端 `nvdec-unsafe` 零 D2D；但尚未覆盖多 slice、真实业务线程/队列、1080p/4K、多流和长稳。Vulkan `h264_nvdec` 的参数集是从 CUVID 字段合成的最小 SPS/PPS，不支持 VUI、crop、非默认缩放矩阵和 POC type 1；这些必须显式失败或进入后续实现。
- 编码链路未验收；实验 D 的“输出码流异常”仍是未解项。
- 目标平台（自研 GPU）未验证；本文所有结果来自 AMD RX 7900 XTX 验证机。

## 一、决策摘要

### 1.1 我们要解决什么问题

客户手里有一批基于 NVIDIA **CUDA**（英伟达的通用计算平台）开发的软件。这些软件在开发时绑定了英伟达的显卡和驱动，换到我们的显卡上就无法运行。

我们的显卡是自研的、基于 AMD 架构，硬件本身没有问题，但缺少"能让 CUDA 软件跑起来"的软件层。让客户把软件**全部重写**成我们的自有接口，成本和周期客户无法接受。

因此，我们要做一个**兼容层**（中间软件），把 NVIDIA 的接口"翻译"成我们自家硬件的接口，让客户的软件以最小的改动代价运行起来。

### 1.2 我们的做法

| NVIDIA 能力 | 我们翻译到 | 当前承诺范围 |
|---|---|---|
| **NVDEC/CUVID**（视频解码） | Linux 标准视频接口 **VAAPI**（备选 **Vulkan Video**） | H.264 / NV12 格式的约定解码接口 |
| **NPP**（图像处理库） | AMD 计算接口 **HIP** | FFmpeg 实际用到的 3 个函数 |
| **libcuda**（底层运行库） | HIP 运行时 | 仅支撑上述两条链路的必要子集 |

> 编码（NVENC）、完整 CUDA 生态、用户自有计算逻辑的自动翻译，**不在当前交付范围内**（详见 §8.3）。

### 1.3 当前状态：方向已验证，端到端尚未打通

| 关键结论 | 证据强度 | 对决策的含义 |
|---|---|---|
| VAAPI 能胜任解码工作 | 已实测（AMD） | 15 种格式对比无短板，5 种专业格式反而更强 |
| 两套驱动栈能共享显存（不经过 CPU 中转） | 已实测（AMD） | "显存直通"的基础已打通 |
| 解码出的画面能被计算侧正确读取 | 已实测（AMD） | 逐字节校验一致 |
| 解析器（最复杂的部分）已复用现成方案 | 已实测（AMD） | I / IP / IPB 三种码流解析通过 |
| NVIDIA 图像处理库的参考基准 | 已实测（NVIDIA） | 3 个关键函数的基准输出已固化 |
| Vulkan Video 备选后端 | 已实测（AMD） | 解码→拷贝→导出→HIP 读，I/IP/IPB 各 30 帧逐字节一致；已接入转接库（`CUVID_SHIM_BACKEND=vk`），FFmpeg `h264_cuvid` 宿主跑通（Tier 2 备选，默认仍 VAAPI） |
| **完整"解码 + 图像处理"端到端链路** | **尚未完成** | **下一步的主要工作** |

**证据强度说明**：
- **已实测（AMD/NVIDIA）**：在指定机器上跑过验证程序，结果通过；仅证明"已测过的项目和平台"。
- **设计假设**：有架构依据或局部实验支撑，但关键链路还没完整跑通。
- **待验证**：尚未提供证据，需作为后续阶段的完成条件跟踪。

### 1.4 建议的下一步

把已经跑通的三个部分（解码、共享显存、解析）拼进兼容层，接上 **FFmpeg**（业界最常用的视频处理软件）完成端到端验收——这是从"证明可行"到"可以交付"之间剩下的最后一公里。

## 二、背景：为什么要做这个兼容层

### 2.1 NVIDIA 的生态锁定

NVIDIA 把"硬件 + 驱动 + 软件开发包（SDK）+ 用户的代码"绑成了一个整体。一个基于 CUDA 开发的软件，通常同时依赖三层东西：

1. **客户自己写的计算代码**：这是客户的核心业务逻辑。
2. **NVIDIA 提供的闭源加速库**：视频解码（NVDEC/CUVID）、图像处理（NPP）等，是 NVIDIA 写好后以二进制形式分发、客户直接调用的现成库。
3. **底层驱动与运行库**：前两层的共同地基。

这三层都深度依赖 NVIDIA 的驱动和硬件，不是"换个编译器"就能跑起来的普通代码。

### 2.2 新厂商的困境与选择

我们（一家新的显卡厂商）的用户态驱动基于开源框架 **Mesa** 开发，硬件指令集为 AMD 的 GFX 架构。硬件能跑，但客户手里已有的 CUDA 软件在 NVIDIA 之外的显卡上跑不起来。

兼容有两种做法，我们**明确选择更务实的一种**：

| 层次 | 含义 | 代价 | 我们的选择 |
|---|---|---|---|
| **二进制兼容** | 客户的可执行文件原封不动，直接替换系统库就能跑 | 要求底层接口（ABI）完全一致，最难 | ✗ 不做 |
| **源码级重编译** | 客户源码基本不改，用我们的头文件/库重新编译 | 改动小，可行 | ✓ **做这个** |

**关键含义**：我们不做"让现有 FFmpeg 等二进制直接运行"，而是让客户**重新编译后能跑**。这大幅降低了兼容难度，但仍需保证**函数名称、参数结构、错误码**等与 NVIDIA 一致，否则客户编译时会出问题。

## 三、技术方案

### 3.1 双轨架构

针对上面提到的两层依赖，兼容策略自然分成两条**互补（而非互斥）**的路线：

```
客户 CUDA 软件源码
        │
        ├─ A. 调用 NVIDIA 现成的库（解码/图像处理…）
        │      └─ 路线 2：我们自己写"转接库"（shim），把调用转到自家实现
        │
        └─ B. 客户自己写的计算代码
               └─ 路线 1：用 HIPIFY 工具自动翻译成 AMD 代码（HIP）
```

| 路线 | 工具/产物 | 管什么 |
|---|---|---|
| **路线 1：HIPIFY 翻译** | HIPIFY（AMD 提供的源码翻译工具）+ HIP | 客户自己写的计算代码 |
| **路线 2：自研转接库** | 我们写的 `libcuda` / `libnvcuvid` / `libnpp*` | NVIDIA 现成库的接口 |

> **为什么不能只用 HIPIFY**：HIPIFY 只能翻译"存在 AMD 对应物"的接口（比如内存分配）。NVIDIA 的解码/图像处理库是闭源的、没有 AMD 对应物，只能靠我们自己写转接库来接。**当前交付只聚焦路线 2；路线 1（用户计算代码）移到后续阶段。**

### 3.2 三条候选路线，我们选了哪条

| 方案 | 思路 | 结论 |
|---|---|---|
| **方案一：转接库 + VAAPI**（主流做法） | 自己写转接库，把解码调用转到 Linux 标准的 VAAPI 视频接口 | **✓ 主线，已投入验证** |
| 方案二：改 Mesa 底层 | 直接在开源驱动框架 Mesa 里新增一套贴近 CUDA 的接口 | ✗ 不采用（要长期维护一个 Mesa 分支，成本极高） |
| **方案三：Vulkan Video**（开放标准） | 把解码转到 Vulkan 的视频扩展 | ⭕ 备选（中期或跨平台需求时再启用） |

**为什么选方案一**：VAAPI 是 Linux 上成熟、被广泛支持的视频接口，与 NVIDIA 解码概念接近；实测中其解码能力反而比 NVIDIA 消费级显卡更广（见 §4.1）。方案三的 Vulkan Video 虽然标准开放，但实测发现"显存直通"受限（见 §4.5），故只作备选。

#### VAAPI vs Vulkan Video 对比总表

| 维度 | VAAPI（主线） | Vulkan Video（备选） |
|---|---|---|
| 成熟度 | 很成熟，业界广泛使用 | 较新，解码近年才落地，编码更滞后 |
| 标准与跨平台 | Linux 专用 | 开放标准，跨平台（Linux/Windows/Android） |
| 解码能力（实测） | 完整，部分格式比 NVIDIA 消费卡更强 | 完整（H.264/HEVC 均达标） |
| 显存直通（零拷贝） | ✅ 支持线性输出，真零拷贝 | ❌ 规范锁死分块，需额外转换 |
| 异步同步 | 有候选路线（标准信号桥接） | 同样受限，只能主机同步 |
| 与 CUDA 语义接近度 | 一般 | 更高（显式内存模型天然对齐） |
| 头文件 / 许可 | 全开源 | 全开源 |
| 维护成本 | 低（成熟稳定） | 高（需处理分块转换、驱动年轻） |
| 我们的定位 | **主线，近期落地** | **Tier 2 备选，中期/跨平台时再启用** |

### 3.3 目标数据通路

我们要打通的完整链路，直观如下：

```
客户软件调用 NVIDIA 解码接口
        ↓
我们的转接库（翻译）
        ↓
VAAPI 解码 → 得到画面（存在显存里）
        ↓
通过"显存共享机制"直接把画面交给计算侧（不经过 CPU 中转）
        ↓
HIP / NPP 图像处理 → 客户使用结果
```

这条链路横跨**两套驱动栈**：Mesa（管视频解码）与 ROCm/HIP（管计算）。于是引出本方案最核心的两个技术问题，也是我们投入真机验证的原因：

1. **显存共享**：解码出来的画面在 Mesa 管理的显存里，计算在 HIP 管理的显存里，两套栈之间的数据能否**不经过 CPU 中转**直接共享？
2. **先后顺序（同步）**：视频引擎和计算引擎是两套独立的硬件队列，共享内存之后，**谁先谁后、何时回收**如何保证正确？

## 四、关键风险与验证结论

本章只保留**真正决定项目成败**的风险，并给出验证结论。低概率、或可通过常规工程手段解决的细节问题，不在本章展开。

### 4.1 VAAPI 能否胜任解码工作？（格式能力）

**结论：能（在已测范围内）。** 这是我们能否选 VAAPI 作为后端的前提。

**验证方式**：把 NVIDIA 消费级显卡（RTX 4060）和我们的 AMD 显卡（RX 9070）放在一起，对比 15 种视频格式组合（H.264/HEVC/AV1/VP9/MPEG-2 × 三种色度采样 × 三种位深）的解码能力。

**结果**：10 项一致，**5 项 VAAPI 领先，0 项 NVIDIA 领先**。VAAPI 领先的 5 项全是专业格式（H.264 的 4:2:2/4:4:4/10-bit、HEVC 4:2:2、MPEG-2 4:2:2）——这些是 NVIDIA 消费级显卡人为屏蔽的能力，我们的 AMD 显卡天然支持。纯硬件解码速度也达标（1080p 下 H.264 828 帧/秒、HEVC 1553 帧/秒）。

> **注意**：该结论适用于"已测的格式和这两块测试卡"，不代表覆盖所有 NVIDIA 设备和全部码流特性；实际交付平台仍需按交付范围复测。

### 4.2 两套驱动栈能否共享显存？（显存直通，本方案的核心）

**结论：基础已打通。** 这是整个方案成立与否的最高优先级问题。

**验证方式**：做了三组实验，验证两套栈能否共存、以及显存能否互相传递。

**结果**：
- **共存**：HIP 与 VAAPI 能在同一个进程里一起跑，无冲突。
- **正向传递**（解码 → 计算）：VAAPI 导出的画面能被 HIP 成功导入、映射。
- **反向传递**（计算 → 解码）：HIP 导出的显存能被 VAAPI 接收（走 AMD 的私有接口）。

> **过程提示**：验证中发现一处"内存布局对齐"问题（画面宽度需按 256 对齐），已定位并解决。生产实现需在运行时查询真实布局，而非硬编码。

### 4.3 解码出的画面内容是否正确？（真实数据校验）

**结论：正确。** 光"能传递显存"还不够，必须证明"传过去的内容是对的"。

**验证方式（实验 C）**：在同一进程里完成"真实解码 → 线性画面 → 导出显存 → HIP 读取 → 逐字节对比"，并用三种码流（纯 I 帧 / I+P 帧 / I+P+B 帧）各 30 帧与软解参考比对。

**结果**：**三种码流全部逐字节一致**，且通过了内存池复用、正常结束清理、文件描述符无泄漏检查。这意味着"解码 → 计算"这条底层通路已真实闭环。

### 4.4 解析器（最复杂、工作量最大的部分）

**结论：已复用现成方案，技术可行。**

**风险背景**：NVIDIA 的解码接口要求我们先把视频码流"解析"成硬件能理解的结构（比如分辨率、编码参数、每帧的类型等）。这部分逻辑非常复杂——不仅是参数解析，还涉及**参考帧管理**（解码时需暂存前后帧做预测）和**B 帧重排序**，是全项目工作量最大的部分。

**验证结果**：
- **解析层复用 FFmpeg 现成代码**（FFmpeg 是开源视频框架，其解析代码质量高、可直接静态链接），我们只自写"填充到硬件参数"的部分。
- 实测在 AMD 机器上，I / IP / IPB 三种码流各 30 帧的解析回调全部通过；其中 IPB 码流还验证了参考帧管理（含 B 帧显示顺序重排）。

> **进展**：纯 I 帧 → P 帧 → B 帧已逐级打通。剩余的长期参考、画面裁剪、跳转/清空等特性需在后续补齐，但核心复杂度已被证明可解。

### 4.5 备选方案 Vulkan Video 为何降为备选？

**结论：能力完整，但"显存直通"受限，故只作备选。这个限制是结构性、短期不会消失的。**

Vulkan Video 是开放标准，理论上对开源驱动更友好，实测其解码能力也完整。但有两个限制，且都**不是普通 bug、等新驱动就能修好**：

1. **显存布局不匹配（结构性，无法靠等驱动解决）**：Vulkan 解码输出的画面是"分块"存储（行业内叫 OPTIMAL/tiled），而计算侧只能按"线性"顺序读，两边对不上，必须额外转换。
2. **异步同步不可用**：HIP 不认 Vulkan 的同步信号，只能退回主机同步。

#### 为什么"分块"这件事是无解的

- 底层解码硬件其实**两种都能写**（分块 / 线性），证据就是 VAAPI 那边能直接拿到线性画面。
- 差别在**接口层**：VAAPI 允许你申请"我要线性"；而 **Vulkan 的规范硬性规定解码输出和参考帧必须是"分块"，根本没有"线性"这个选项**。所以不是驱动偷懒，是规范锁死了。
- 更关键的是，计算侧（HIP/CUDA）的内存模型只有"按线性地址读"这一种方式，它**不认识分块排列**——所以哪怕把分块的显存"递"过去，读出来也是错位的（花屏）。

#### 因此三条路，只有一条值得走

| 路线 | 结论 |
|---|---|
| 改 Mesa，让 Vulkan 也输出线性 | ❌ **不推荐**：违反 Vulkan 规范，永远进不了上游，只能永久维护一个私有分支，成本极高 |
| 修改导入接口，让 HIP 读分块 | ❌ **走不通**：分块不是接口问题，是"用哪条硬件通路读"的问题，改接口碰不到这一层 |
| **接受一次转换** | ✅ **推荐**：用显卡自带的**拷贝引擎**（`vkCmdCopyImageToBuffer`），把分块画面直接拷成线性，再交给 HIP |

推荐做法的链路：`Vulkan 解码 → 显卡拷贝引擎转成线性 → 交给 HIP`。这里有一个关键澄清：**分块画面完全可以直接拷**——之前误以为拷贝要求源画面必须是"线性"，其实不是。拷贝要求的是画面处于"可拷贝状态"（通过一次状态切换即可），物理上分块还是线性都无所谓，显卡拷贝引擎自己会正确解分块。代价是每帧多一次显卡内拷贝（4K 一帧约几十到一两百微秒，需实测量化），换取的是**合规、无需维护私有分支**。这条路径已有成熟实现可参考（FFmpeg、GStreamer、AMD 官方样例），详见整合版 §4.4。

#### 异步同步：别去修信号量，改走标准桥接

- 直接修 `hipImportExternalSemaphore`（让 HIP 认 Vulkan 的信号）是**死胡同**：Vulkan 的信号是私有格式，计算栈（ROCm）根本不认识，两边对不上。
- **正解**：改用 Linux 的标准"完成信号"格式（sync_file）桥接——Vulkan 导出标准信号 → 转成内核的同步对象 → ROCm 把它挂成计算队列的等待条件。这条链路的内核部分已经实测可用，缺的是 ROCm 用户态补上"挂接"这一步，属于**与驱动厂商的协同开发项**（详见整合版 §4.12）。

**综合定位**：Vulkan Video 维持 **Tier 2 备选**，仅在中期或跨平台需求时再启用；启用时接受"一次转换 + 主机同步"的成本，不为其维护私有 Mesa 分支。

**实测进展（P0 闭环，2026-11-06）**：上述"解码 → 显卡拷贝引擎转线性 → 交给 HIP"的推荐链路，已在 AMD 验证机（RX 7900 XTX）**端到端跑通并全部通过**——I-only / I/P / I/P+B 三种码流各 30 帧，HIP 读回像素与软件解码参考**逐字节一致**，且无 fd/显存泄漏。这印证了"接受一次转换"这条路**确实可行、合规、无需私有 fork**。但仍只证明"底层数据通路可用"，尚未接回 CUVID shim / FFmpeg 宿主，故 **Tier 2 备选定位不变**。实现细节与 5 个关键约束见整合版 §4.4。

**实测进展（接入转接库与宿主，2026-11-07）**：上一步"尚未接回宿主"已闭合——转接库 `libnvcuvid.so.1` 新增了 **Vulkan Video 解码后端**，与 VAAPI 后端并列，通过环境变量 `CUVID_SHIM_BACKEND=vk` 切换（**默认仍是 VAAPI**）。AMD 验证机实测：三种码流各 30 帧逐字节一致、无 fd 泄漏；FFmpeg 的 `h264_cuvid` 入口跑通 30 帧、0 解码错误。这意味着客户的 NVIDIA 解码调用现在**能经 Vulkan 后端接住**了。但 **Tier 2 备选定位不变**：默认后端仍是 VAAPI；Vulkan 路径下的零拷贝（`h264_nvdec`）、跳转/清空、动态分辨率、以及 HEVC/VP9/AV1 等**尚未在此后端验收**。实现细节与文件清单见整合版 §4.4 及 `docs/architecture/vulkan-backend.md`。

#### 一个重要澄清：换后端，验收宿主不变

Vulkan Video 只是把转接库**内部**的解码翻译目标，从 VAAPI 换成 VK。对客户软件而言，**入口没变**——客户仍通过 NVIDIA 接口（FFmpeg 的 `h264_cuvid` / `h264_nvdec`）调用，所以验收时**仍用这两个入口做宿主**，验证"客户的 NVIDIA 调用能否被 VK 后端接住"。

容易搞混的 `h264_vulkan` 是另一回事：它是 FFmpeg 自带的原生 Vulkan 解码器，**绕过了我们的转接库、直接调 Vulkan**，因此不能作为兼容层的验收证据——最多用来做个环境冒烟（确认显卡的 Vulkan 解码能跑）。据此，转接库应预留一个"解码后端"开关（后端1=VAAPI、后端2=Vulkan Video，运行时可选），宿主和接口保持不变，只有内部后端可换。**该开关已落地**：`CUVID_SHIM_BACKEND=vk` 即切换到 Vulkan 后端，默认仍为 VAAPI。

### 4.6 异步同步能否建立？（先后顺序的进阶方案）

**结论：当前用"主机同步"基线即可，异步留作后续。**

**背景**：视频引擎和计算引擎是两套独立硬件队列，共享显存后不会自动排序。有两种保证顺序的做法：

- **主机同步**（简单稳妥）：由 CPU 显式等待"视频完成 → 再启动计算"。
- **异步同步**（更高效）：让两个硬件引擎之间直接传递"完成信号"，无需 CPU 介入。

**验证结果**：主机同步方案已通过全部 8 项顺序与资源管理测试（含 1000 帧长稳无泄漏）。异步方案所需的底层原语实测可用，但本次 HIP 版本尚不支持直接导入信号，真实跨引擎传递未验证。

**决策**：首期用**主机同步**作为功能基线（正确优先），把"异步同步"列为与驱动厂商的协同开发项，不阻塞当前交付。

### 4.7 图像处理库（NPP）的法律与数值一致性

**结论：参考基准已建立，实现待完成。**

NPP 是 NVIDIA 的图像处理库，我们要复刻 FFmpeg 实际用到的 3 个函数。这里有两个关键点：

1. **法律合规**：NPP 的头文件是 NVIDIA 的专有授权，不能随我们的产品分发。**对策**：我们只产出库文件（`.so`），构建时使用客户另行提供的授权头文件，发布物不含专有内容。
2. **数值一致**：同样的输入，我们的实现要和 NVIDIA 输出**逐字节一致**（尤其图像缩放、颜色格式转换这类对像素敏感的函数）。

**验证结果**：已在 NVIDIA 参考机（RTX 4060）上，用 NPP 11.5 版本生成 3 个函数的基准输出并固化校验值。**接下来**：在 AMD 上用 HIP 重新实现这 3 个函数，并逐字节对齐该基准。

### 4.8 能否从测试机移植到实际交付平台？（可移植性）

**结论：这是当前最需要盯的风险，须在交付前完成复测。**

**背景**：我们已验证的结论基于 AMD 测试机（RX 7900 XTX + 特定的驱动/系统版本）。AMD 的私有接口可用性已确认，不再是阻塞项；但显存布局、性能表现、驱动版本等**不能直接外推**到实际交付的硬件和软件栈。

**对策**：实际交付硬件、驱动或软件栈一旦确定，必须重新验证"共存、共享显存、线性画面、真实像素、同步、性能"这一整套门禁。这是交付前的硬性前提，已在路线图中明确。

## 八、附录

### 8.1 术语表

| 术语 | 通俗解释 |
|---|---|
| CUDA | NVIDIA 的通用计算平台 |
| NVDEC / CUVID | NVIDIA 的视频解码接口 |
| NPP | NVIDIA 的图像处理库 |
| VAAPI | Linux 标准的视频硬件加速接口 |
| HIP / ROCm | AMD 生态的计算接口 / 计算平台（对标 CUDA） |
| Mesa | Linux 开源显卡驱动框架 |
| Vulkan Video | 开放标准的视频编解码接口（Khronos 制定，跨平台） |
| shim / 转接库 | 把 NVIDIA 接口翻译成自家接口的中间库 |
| FFmpeg | 业界最常用的开源视频处理软件 |
| H.264 / NV12 | 视频编码格式 / 像素颜色格式 |
| I / P / B 帧 | 视频帧类型（I 关键帧、P 前向预测帧、B 双向预测帧） |
| 解析器（parser） | 把视频码流解析成可解码结构的组件 |
| 参考帧缓存（DPB） | 解码时暂存前后帧用于预测的缓冲区 |
| 显存直通（零拷贝） | 不经过 CPU 中转、直接在显存里共享数据 |
| 显存共享（DMA-BUF） | 让不同驱动共享同一块显存的标准机制 |
| 同步 | 保证不同硬件队列按正确先后顺序执行 |
| 分块存储（OPTIMAL/tiled） | 把画面切成小块交错存放，硬件读得快、但无法按线性地址直读 |
| 完成信号（semaphore/fence） | 跨引擎传递"我干完了"的标记，用于异步同步 |
| ABI | 二进制接口兼容（函数调用约定、数据结构布局等） |
| HIPIFY | AMD 提供的源码自动翻译工具（把 CUDA 代码翻译成 HIP 代码） |

### 8.3 当前非目标（明确不做的事）

- 视频编码（NVENC）及编码链路
- H.264 之外的其他编码格式（HEVC、AV1、VP9 等）、10/12-bit、4:2:2/4:4:4 色度
- 完整 CUDA 生态、完整 NPP、任意客户应用的兼容
- 客户自有计算代码的 HIPIFY 自动翻译（移到后续阶段）
- 二进制兼容（客户可执行文件不重编译直接运行）
- 场/MBAFF（一种隔行编码特性，遇到时明确返回"不支持"）
- 异步同步、多 GPU、跨进程显存共享；Vulkan Video 已证明底层解码通路可行并接入转接库（§4.5，`CUVID_SHIM_BACKEND=vk`），但**不作为交付范围**，仅作 Tier 2 备选

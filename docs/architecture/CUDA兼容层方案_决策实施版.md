## 一、背景与目标

### 1.1 业务背景

客户已有视频软件通常依赖三类 NVIDIA 能力：

- **视频解码**：NVDEC/CUVID；
- **图像缩放和格式转换**：NPP；
- **设备、内存和队列管理**：CUDA 底层接口。

这些能力绑定 NVIDIA 驱动和硬件，无法仅靠更换编译器迁移到我们的 GFX/AMD 架构显卡。如果让客户全部重写，业务代码、测试体系和发布流程都要重建，迁移成本高，也会延缓新硬件导入。

本项目需要解决的是：

> 用多大的客户改动和厂商投入，让既有视频业务在自研显卡上正确、稳定、可维护地运行。

### 1.2 项目目标

在约定范围内，让客户现有基于 CUDA 的视频处理软件，以可接受的迁移成本在我们的显卡上完成“视频解码 → 图像处理”，并满足以下要求：

- 解码和图像处理结果正确；
- 优先通过显存共享减少 CPU 数据中转；
- 规定场景下运行稳定，资源能够正确释放；
- 实际自研平台上完成性能和业务验收；
- 构建、发布和后续维护责任明确。

### 1.3 需要作出的决策

1. 客户保留原二进制直接运行，还是接受源码重编译？
2. 如果选择源码重编译，视频解码和资源管理采用哪种实现方案？
3. 当前兼容层与长期自有 SDK 如何分工？

## 二、兼容方式对比与选择

当前有两种主要兼容方式：**二进制直接兼容**和**源码级重编译兼容**。

### 2.1 二进制直接兼容

#### 工作方式

客户不重新编译，保留原可执行文件和已有依赖，通过相同库名、导出符号和二进制约定加载我们的实现。

二进制兼容又可以分为：

1. **固定宿主二进制兼容**：只支持某个明确版本、构建配置的 FFmpeg 或客户程序。
2. **通用二进制兼容**：支持不同应用和版本直接替换 NVIDIA 库，接近长期生态建设。

#### 优点

- **客户改动最少**：不需要源码、构建环境和重新发布应用。
- **覆盖无源码场景**：适合固定软件包、设备厂商程序或无法取得构建权的客户。
- **固定宿主可以收敛范围**：如果业务只需一个冻结版本，可围绕真实调用行为进行针对性实现。

#### 缺点

- **实现和验证成本最高**：不仅要有同名函数，还要匹配结构布局、调用约定、回调、版本行为、错误码和资源生命周期。
- **问题更晚暴露**：源码构建阶段能够发现的部分不一致，在二进制场景中可能延到运行期，表现为崩溃或数据错误。
- **测试组合容易膨胀**：不同宿主版本、编译选项和依赖库组合，可能产生不同的二进制行为。
- **通用兼容难以收敛**：固定 FFmpeg 的成功不能推导出任意 CUDA 应用可直接运行。
- **法律审查更复杂**：若涉及专有库分发、闭源实现逆向或替换加载，需要分别确认合同、授权和司法辖区边界。
- **客户预期更高**：客户容易把“不重编译”理解为“任何版本都不用调整”，售后和支持责任随之扩大。

#### 成本判断

在已有后端能力可复用的前提下，**固定宿主二进制兼容粗估仍需 6～12 个月、4～6 名核心人员及专项测试/法务投入**。通用 CUDA 二进制生态不适合纳入当前项目承诺，需要独立长期立项。

### 2.2 源码级重编译兼容

#### 工作方式

保留客户主要 CUDA/CUVID/NPP 调用方式，由客户使用我们的头文件、库和构建说明重新编译。底层可以采用 VAAPI、Vulkan Video 或 Mesa 新增 frontends 适配。

```text
客户已有源码
      │ 保留主要业务逻辑和 NVIDIA 调用方式
      │ 调整头文件、链接库、加载路径及必要构建配置
      ▼
重新编译后的客户程序
      │
      ▼
我们的兼容实现 → 自研显卡驱动与计算能力
```

#### 优点

- **范围可以明确收敛**：围绕指定源码、宿主版本和真实接口清单实现，不必承诺所有旧二进制。
- **部分问题可在构建期发现**：函数声明、类型和链接不一致可以更早暴露，降低运行期不确定性。
- **与现有研发基础一致**：当前 CUVID、NPP、libcuda 和底层实验均以限定接口和宿主为基础。
- **近期投入相对可估**：采用转接库路线时，现有验证成果可以继续复用。
- **法律责任相对可控**：不以兼容所有 NVIDIA 闭源二进制行为为目标，但仍需处理头文件和开源许可。

#### 缺点

- **客户必须有源码和构建能力**：只有二进制或构建环境不可恢复时无法采用。
- **客户并非零成本**：仍需修改构建、重新发布并完成业务、数值、稳定性和性能回归。
- **并非没有二进制约束**：FFmpeg 动态加载仍要求库名、符号、函数参数、回调和相关数据结构匹配。
- **需要持续版本维护**：FFmpeg、Mesa、ROCm、驱动和客户头文件变化都可能形成适配工作。
- **容易形成范围蔓延**：不同客户使用不同接口，如果都纳入支持，项目会从有限兼容扩张为生态工程。

#### 成本判断

源码兼容本身不决定周期，仍取决于底层实现：

- VAAPI 转接一期粗估 **8～10 周**；Vulkan Video 转接一期粗估 **10～12 周**；
- Mesa 新增 frontends 适配：粗估 **6～12 个月**；
- 客户侧应用构建和业务回归另计，不能包含在厂商研发周期中。

### 2.3 综合对比

| 对比维度 | 二进制直接兼容 | 源码级重编译兼容 |
|---|---|---|
| 客户前提 | 无需源码，但需冻结宿主和依赖版本 | 需要源码、构建权和可恢复的构建环境 |
| 客户改动 | 原则上无 | 以构建适配为主，仍需重新发布和业务回归 |
| 厂商实现范围 | 二进制接口、行为、版本及加载约定 | 真实源码调用面及必要的动态加载约定 |
| 问题发现时间 | 更多集中在运行期 | 部分可提前到编译和链接期 |
| 验证规模 | 高，宿主和依赖组合敏感 | 相对可控，可锁定源码和构建版本 |
| 固定范围粗估周期 | 6～12 个月 | 转接方案 8～12 周（VAAPI 8～10；Vulkan 10～12）；Mesa 方案 6～12 个月 |
| 长期维护 | ABI 与宿主版本矩阵，成本高 | 接口和依赖回归，成本中等 |
| 法律重点 | 另可能涉及专有库分发、逆向和替换加载边界 | 头文件授权、开源许可、专利及兼容宣传 |
| 最适合场景 | 客户完全无法提供源码或修改程序 | 客户可重编译，希望以较少改动完成迁移 |

### 2.4 选择结论：本期采用源码级重编译兼容

**本期放弃二进制直接兼容，采用源码级重编译兼容。** 主要理由如下：

1. **当前目标是限定链路，不是通用二进制替换。** 一期只需覆盖 FFmpeg 7.1 的 H.264 解码和 3 个图像处理函数。为此承担完整二进制行为兼容，新增成本大于当前业务收益。
2. **现有验证成果更适合源码兼容。** 当前接口清单、FFmpeg 宿主、NPP 参考和底层实验都可直接复用，没有必要另起一套通用 ABI 兼容工程。
3. **源码兼容能缩小验证范围。** 通过锁定源码、构建配置和版本，可以把主要精力用于真实像素、业务稳定性和目标平台，而不是大量宿主二进制组合。
4. **周期更符合近期业务导入。** 转接方案可按约 3～4 个月规划，固定二进制兼容通常需要额外数月甚至更长时间。
5. **法律与发布边界更容易管理。** 当前不需要以逆向 NVIDIA 闭源库或支持其任意二进制行为为前提，可以集中处理授权头文件、FFmpeg LGPL 和对外兼容声明。
6. **仍保留后续扩展可能。** 若未来出现无法重编译的重点客户，可在已完成的兼容实现上，单独评估固定宿主二进制支持，而不是现在预先承担通用兼容成本。

**这一选择的关键前提是：目标客户必须能够提供源码、构建环境和业务回归条件。** 该条件应在项目启动前由客户书面确认。若核心客户只能提供二进制，则应重新评估二进制兼容，不能把源码方案包装成“无需修改”。

## 三、业务范围、业务价值与验证基础

### 3.1 统一业务范围

后续三种技术方案均按以下范围比较：

| 维度 | 统一比较范围 |
|---|---|
| 业务链路 | H.264 视频解码 → 图像缩放/像素平面转换 → HIP 侧读取或使用 |
| 验证宿主 | FFmpeg 7.1；`h264_cuvid` 与 `h264_nvdec` |
| 视频格式 | H.264、8-bit、4:2:0、NV12 |
| 图像处理 | `nppiResizeSqrPixel_8u_C1R`、`nppiYCbCr420_8u_P2P3R`、`nppiYCbCr420_8u_P3P2R` 及必要支撑 |
| 码流与场景 | I/P/B、参考帧、裁剪、跳转/清空、动态分辨率、长期参考；1080p/4K、1 路和 8 路 |
| 数据通路 | 优先在显存内完成解码到计算的数据交接，避免 CPU 中转 |
| 稳定性 | 1 路和 8 路分别运行 30 分钟，无崩溃、死锁、非法访问或持续资源增长 |
| 平台 | 最终必须在实际自研目标平台验收，AMD 验证机结果只作为技术依据 |

视频编码、其他编码格式、完整 NPP、完整 CUDA、多 GPU 和跨进程共享不纳入本轮比较；如需加入，应重新估算。

### 3.2 业务价值与衡量方式

| 业务目标 | 源码重编译兼容的价值 | 建议衡量指标 |
|---|---|---|
| 缩短客户导入周期 | 保留主要业务代码，避免整体重写 | 客户源码改动量、适配人周、从拿卡到业务上线的时间 |
| 扩大自研硬件可服务的软件范围 | 让既有 CUDA 视频业务可在自研平台运行 | 完成验收的应用数、客户数和业务场景数 |
| 降低系统运行开销 | 显存直通减少 CPU 中转，合理后端提升多路处理效率 | 总吞吐、单帧延迟、CPU/显存占用和单位流处理成本 |
| 控制迁移风险 | 在明确版本和接口清单内逐步验收，而非一次性替换整个生态 | 构建适配项数、回归通过率、缺陷修复周期 |
| 为长期自主平台争取时间 | 先承接存量业务，再逐步建设自有 SDK 和原生应用 | 原生组件复用率、迁移到自有 SDK 的应用数 |

零拷贝的收益必须用完整业务链路测量，不能用单项硬件解码速度代替业务收益。

### 3.3 已有验证基础

| 验证项 | 当前结果 | 能支持什么判断 |
|---|---|---|
| VAAPI 格式能力 | 历史批次对比 15 组格式，VAAPI 与 RTX 4060 有 10 项一致、5 项领先、0 项落后 | VAAPI 具备后端能力；不代表范围之外也承诺支持 |
| VAAPI 与 HIP 共存 | 可在同一进程工作，显存可导出、导入和映射 | 跨驱动显存共享架构可行 |
| VAAPI 真实解码到 HIP | I、I/P、I/P/B 三类码流各 30 帧，HIP 读回与软件参考逐字节一致 | 底层数据通路和像素正确性已验证 |
| 线性画面 | 320×240 至 4K 的已测样本内容正确，未观察到明显解码耗时回退 | VAAPI 可优先采用无需额外转换的线性直通 |
| H.264 解析 | FFmpeg 解析可复用；参考帧复用和 B 帧显示重排已通过 | 解析器不必完全从零开发 |
| 主机同步 | 8 项顺序与资源测试通过，包含 1000 帧运行和文件句柄检查 | 可先由 CPU 保证解码、计算和回收顺序 |
| libcuda 子集 | 82 个符号形态、47 项功能子集测试有通过记录 | 可作为继续开发基础，不等于完整 CUDA 兼容 |
| NPP 参考 | RTX 4060 + NPP 11.5.1.107 的 3 个函数参考输出已固化 | 后续实现有明确数值对照 |
| **P0 双后端闭环（2026-11-12）** | **四路码流：VAAPI 82/82、Vulkan 82/82 逐字节一致（合计 164 帧）；`verify_kernel_read` errors=0；`make check` / `check_func` / parser / session 全 PASS；Vulkan B 帧挂死已修复** | **两条后端的数据通路和 mapped pointer kernel 读取已闭环；FFmpeg 宿主双路径、NPP 和业务链路尚未验收** |

### 3.4 尚未完成的工作

1. FFmpeg 宿主双路径（`h264_cuvid` / `h264_nvdec`）的像素与零拷贝验收；shim 的 decode/map/kernel 读取已通过 `verify_kernel_read`。
2. 3 个 NPP 函数的 HIP 实现及与 NVIDIA 参考逐字节一致。
3. 完整“解码 → 图像处理”业务链路。
4. 复杂码流、1/8 路、实际自研平台、真实业务性能及生产发布验收。
5. Vulkan 后端的 `h264_nvdec` 零拷贝、多流、跳转/清空和目标平台验收。

**阶段判断：P0 双后端数据通路已闭环，底层可行性证据较强；产品可行性（NPP、FFmpeg 宿主、业务链路）尚待闭环。** 现有成果可以降低两种转接库方案的技术不确定性，但不能证明任何方案已经生产可用。

### 3.5 证据使用边界

Vulkan 后端的 AMD 结果来自 2026-11-07 的方案回写；P0 双后端结果来自 2026-11-12 的 AMD 验证运行。`docs/evidence/P0闭环验证结果_2026-11-12.md` 先记录了结果汇总，四路码流已入库 `testdata/h264/`；原始日志、命令和 SHA256 仍需补归档后，才能转成正式验收证据。

## 四、源码重编译兼容的三种技术方案

三种方案都以客户可重编译为前提，都需要完成 NPP、libcuda、目标平台和业务验收，区别主要在视频解码及驱动实现方式。

### 4.1 VAAPI 转接方案

#### 工作方式

转接库将视频解码转到 VAAPI，将图像处理转到 HIP。H.264 解析复用 FFmpeg，自写与 VAAPI 的参数衔接；一期由 CPU 显式控制解码和计算顺序。

```text
客户源码 / FFmpeg 源码
        │ 重新编译、链接或动态加载转接库
        ▼
CUVID/NPP/CUDA 转接库
        ├─ 解码 → VAAPI → 线性显存画面
        └─ 图像处理 → HIP
                         ▲
                  显存直接共享，不经过 CPU
```

#### 优点

- **客户业务改动较少**：不需要把业务逻辑整体改写为新接口。
- **现有底层证据较完整**：真实解码、线性显存共享和 HIP 像素校验均已通过。
- **数据通路较短**：线性画面可直接给 HIP 读取，不需要额外画面转换。
- **驱动生态成熟**：VAAPI 在 Linux 视频领域应用广泛，不需要修改 Mesa 内部架构。
- **近期工作量相对可估**：剩余工作主要是主线集成、NPP、复杂场景和平台验收。

#### 缺点

- **主要面向 Linux**：其他操作系统需要新增后端或另建方案。
- **接口映射仍需完成**：CUVID 参数、回调、错误行为和资源生命周期都要准确衔接。
- **FFmpeg 内部解析代码带来版本和许可责任**：升级要回归，发布要履行 LGPL 义务。
- **长期需要兼容维护**：FFmpeg、Mesa、ROCm 或客户接口变化都可能形成适配工作。
- **完整端到端性能尚未证实**：底层零拷贝通过不等于多路业务性能达标。

#### 适用条件

业务运行在 Linux；希望控制近期迁移成本；接受限定接口和版本的兼容产品，而非完整 CUDA 生态。

### 4.2 Vulkan Video 转接方案

#### 工作方式

客户侧与 VAAPI 转接方案相同，转接库内部将 CUVID 解码请求转到 Vulkan Video，再把解码后的分块画面在显卡内转换为 HIP 可读的线性数据。

```text
客户源码 / FFmpeg 源码
        │ 重新编译
        ▼
CUVID/NPP/CUDA 转接库
        ├─ 解码 → Vulkan Video
        │             └─ 显卡内转换为线性画面
        └─ 图像处理 → HIP
                         ▲
                    显存共享
```

现有工程已提供运行时后端开关 `CUVID_SHIM_BACKEND=vk`，但工程默认设置不代表管理层已完成选型。

#### 优点

- **开放标准和跨平台潜力**：适合未来存在 Windows、Android 或多个 GPU 厂商需求的业务。
- **客户迁移方式与 VAAPI 相同**：保留主要业务调用方式。
- **显式和标准化的资源管理**：有利于跨后端抽象和后续平台扩展。
- **已有真实实现基础**：底层像素通路已验证，报告记录已接入 CUVID 转接库和 FFmpeg `h264_cuvid`。
- **不需要维护私有 Mesa 分支**：画面转换可通过标准 Vulkan 拷贝能力完成。

#### 缺点

- **多一次显卡内数据转换**：分块解码输出不能直接按 HIP 普通指针读取，完整业务转换开销尚未量化。
- **当前兼容覆盖不完整**：`h264_nvdec` 零拷贝、多流、跳转/清空、动态分辨率等仍需实现和验收。
- **实现链路更复杂**：解码队列、转换队列和资源生命周期需要共同管理。
- **平台能力依赖更强**：不同系统的视频扩展、驱动成熟度和格式支持需要分别验证，跨平台不等于开箱即用。
- **同步增强仍缺现成通路**：当前同样以主机同步为基线，跨引擎异步信号需要额外协同。
- **法律与维护责任不会因换后端而消失**：NPP、FFmpeg 解析和接口兼容问题仍然存在。

#### 适用条件

跨平台是明确的中期业务需求；团队接受额外转换和更复杂的实现；愿意按平台分别投入性能和兼容性验证。

### 4.3 Mesa 新增 frontends 适配方案

#### 工作方式

不只在驱动外增加转接库，而是在 Mesa 内新增接近 CUDA 语义的入口，让驱动直接承接视频兼容。NPP 和必要计算能力仍需另行实现。

```text
客户源码
   │
   ▼
CUDA 风格驱动入口 → Mesa 内部视频实现 → 硬件
   │
   └─ NPP / 计算仍需 HIP 或其他组件配合
```

> **名称说明**：本方案指在 Mesa 内新增接近 CUDA 语义的 frontends，而不是对 Mesa 做泛化的“深度改造”。改名是为了准确描述接口层工作；驱动内实现、上游/私有分支维护和完整驱动回归的成本仍按原判断，不因名称调整而降低。

#### 优点

- **行为控制力较强**：驱动内部可以直接管理会话、内存、队列和资源生命周期。
- **有潜在性能优化空间**：可针对硬件设计更直接的数据路径。
- **可能形成平台级能力**：若设计通用且能进入上游，可服务多个上层应用。
- **对外接口可统一规划**：适合将视频兼容作为长期驱动战略的一部分。

#### 缺点

- **实施周期和人员要求高**：需要熟悉 Mesa、视频硬件、内存和队列的驱动团队。
- **长期分支维护成本高**：若上游不接受，需要持续维护私有分支并跟随 Mesa 升级。
- **上游接受存在协调成本**：接口是否足够通用、是否符合上游方向，不只是编码问题。
- **不能自动解决 NPP 或客户计算代码**：图像处理、HIP 联合链路和 HIPIFY 仍需独立投入。
- **测试面扩大到驱动层**：还需承担驱动回归、多版本兼容和发布责任。
- **不天然解决上层接口约束**：符号、结构和错误行为仍需对齐。

#### 适用条件

公司拥有稳定驱动团队；视频兼容属于长期平台战略；能够承担上游维护或私有分支成本；对上市时间的要求允许较长投入。

## 五、三种技术方案综合对比

### 5.1 核心对比表

> 周期为从当前状态完成第三章相同业务口径的粗估，不是报价或固定承诺，均包含当前 3 个图像处理函数。

| 对比维度 | VAAPI 转接 | Vulkan Video 转接 | Mesa 新增 frontends 适配 |
|---|---|---|---|
| 客户业务代码改动 | 少，以构建适配为主 | 少，以构建适配为主 | 少，以构建适配为主 |
| 当前底层证据 | 真实解码、线性直通、HIP 像素通过 | 解码、转换、HIP 像素通过；单宿主路径有记录 | 尚无同口径实现证据 |
| 解码到 HIP 数据通路 | 可直接使用线性画面 | 需要额外显卡内转换 | 可直接设计，需实测 |
| 当前主要工程缺口 | VAAPI CUVID 主线、NPP、双路径 | Vulkan 完整覆盖、转换性能、NPP | 驱动入口及全部配套 |
| 跨平台潜力 | Linux 为主 | 较强，但需逐平台验证 | 跟随 Mesa 和目标系统 |
| 近期实施难度 | 中 | 中到较高 | 高 |
| 长期维护成本 | 中：接口与依赖回归 | 中到较高：增加后端和平台矩阵 | 高：驱动分支或上游维护 |
| NVIDIA 相关法律暴露 | NPP 头文件、兼容声明等 | 与 VAAPI 基本相同 | 与 VAAPI 基本相同 |
| 开源许可责任 | FFmpeg LGPL、第三方声明 | 与 VAAPI 相近，另有 Vulkan 组件 | Mesa、FFmpeg 及其他组件 |
| 粗估剩余周期 | **8～10 周** | **10～12 周** | **6～12 个月** |
| 核心人员估算 | 4.0～4.5 FTE（核心 3 人 + 测试/构建 1.0～1.5） | 3.5～5 FTE（3～4 人 + 0.5～1 测试） | 4～6 人 + 驱动测试 |
| 战略价值 | 快速形成 Linux 兼容能力 | 形成开放、跨平台后端能力 | 形成更深的平台驱动能力 |

> 表中周期为一期（功能兼容验收）口径：VAAPI 一期 8～10 周，二期 4～6 周，合计 12～16 周（约 3～4 个月）。二期客户应用、自研平台回归和生产发布另计，详见第七章。

### 5.2 不能只看研发周期

**项目总成本 = 厂商研发成本 + 客户构建与回归成本 + 双方测试成本 + 后续维护成本。**

- VAAPI 与 Vulkan Video 的周期差不大时，跨平台战略和长期维护可能比一期多几周更重要。
- Mesa 新增 frontends 适配的额外投入只有在能服务多个产品或多个客户时，才更容易体现规模价值。
- 每增加一个正式支持的后端，都需要独立的像素、稳定性、性能和平台验收。
- 实验性后端可以低成本保留，**正式产品支持则意味着持续维护**。

### 5.3 HIPIFY 与三种方案的关系

客户自己写的 CUDA 计算代码，可考虑用 HIPIFY 转成 HIP，再由人工完成数值验证和性能调优；NVIDIA 的解码和 NPP 库没有可直接翻译的完整 HIP 对应实现。

因此，HIPIFY 是三种方案都可能使用的补充工具，**不能单独替代视频解码和图像处理兼容方案**。若客户包含内联 PTX、特殊指令或闭源依赖，迁移工作量需另行评估。

## 六、源码级兼容的成本与风险

### 6.1 客户侧成本与适用限制

| 项目 | 实际影响 | 决策前需要确认 |
|---|---|---|
| 源码与构建权 | 没有源码、构建脚本或第三方库构建权时，无法采用 | 客户是否能从干净环境重建当前产品 |
| 构建适配 | 需要调整头文件、链接库、加载路径和版本检查 | 改动能否进入客户正式构建和发布流程 |
| 业务回归 | 即使业务源码不改，也需重跑功能、数值、稳定性和性能测试 | 客户是否接受重编译后的新版本及验收成本 |
| 自有 CUDA kernel | HIPIFY 后仍可能有人工修改、数值差异和性能调优 | 是否含内联 PTX、特殊指令、闭源库或复杂流控制 |
| 版本锁定 | 客户升级宿主或 CUDA 头文件可能超出已验证范围 | 支持版本清单和升级政策由谁承担 |

对于接口集中、构建可控且无复杂自有 kernel 的应用，客户侧首次适配和回归可按 **2～6 周**初步规划；复杂应用必须依据源码扫描和试点重新估算。该时间不包含在厂商兼容层一期 8～12 周研发估算内。

### 6.2 时间与人力风险

**1. 符号完成不等于功能完成。**  
主要工作量在解析、参考帧、映射、同步、错误行为和资源回收，而不在导出函数名。NPP 的舍入、边界和内存布局也可能产生数值差异。

**2. 长尾场景决定能否交付。**  
裁剪、跳转、动态分辨率、长期参考、多路运行和异常恢复会集中暴露状态管理问题。只验证 30 帧正常码流，无法支撑生产周期承诺。

**3. 目标平台可能改变剩余工作量。**  
AMD 验证机已证明架构方向，但自研平台的显存布局、驱动能力和性能需要重新验证。若底层能力缺失，工作会从应用兼容扩展到驱动协同。

**4. 版本维护是持续成本。**  
首个版本后建议预留 **0.5～1 名工程师**用于兼容回归、缺陷和版本适配；每次 FFmpeg、Mesa 或 ROCm 关键升级，可初步预留 **1～3 周**评估与回归，重大内部接口变化另计。

**5. 多客户会扩大接口面。**  
FFmpeg 使用 3 个 NPP 函数，不代表其他客户也只使用这 3 个。新客户接入前必须扫描真实调用清单，否则“小范围兼容”会在交付中不断扩张。

### 6.3 仍存在的二进制接口风险

源码级重编译消除了“所有旧二进制完全不动”的要求，但以下约束仍在：

- FFmpeg 会动态查找 CUDA/CUVID 符号，缺少必需符号会导致加载失败。
- 函数参数、返回值、回调约定和相关数据结构必须与构建时使用的头文件一致。
- 库名、SONAME、导出符号后缀和版本行为需匹配宿主预期。
- 错误码不能简单透传 HIP；不支持的能力必须明确失败，不能返回伪成功。
- 如果承诺某个已编译二进制可直接加载，就同时进入了二进制直接兼容的验收范围，不能只按源码兼容估算。

### 6.4 法律与合规风险

> 以下为工程和产品风险提示，正式分发条件须由法务结合具体许可证、合同和发布物审查。

| 风险项 | 具体问题 | 可选处理方式及代价 |
|---|---|---|
| NVIDIA CUDA/NPP 头文件授权 | NPP 头文件属于专有许可，不能因为“实现由我们重写”就默认可复制和再分发 | 由有授权的一方提供头文件；分别确认构建使用权、兼容实现权和产物分发权；发布物不附带未获许可的专有头文件 |
| 独立实现与知识产权 | 仅重写代码不自动排除专利、接口声明来源或许可合同问题 | 保留独立实现记录，不复制 NVIDIA 闭源代码；必要声明和专利问题由法务评审 |
| FFmpeg LGPL 静态复用 | 当前解析复用依赖 FFmpeg 内部对象，静态组合可能产生对应源码、构建信息和再链接材料义务 | 使用 `--disable-gpl --disable-nonfree --enable-pic` 的干净构建；保留对应源码、构建脚本和适用的再链接材料；发布前做法务检查 |
| Mesa/libva/Vulkan/ROCm 等组件 | 开源不等于无义务，仍可能要求保留版权和许可声明 | 建立组件清单、许可证和版权声明；随发布物提供必要材料 |
| 编解码专利 | 开源许可证不当然替代 H.264 等编解码专利许可 | 确认硬件、软件及目标销售地区的既有专利覆盖，不能用“驱动开源”作为充分依据 |
| 商标与兼容宣传 | “完整 CUDA 兼容”“NVIDIA 认证”等表述可能造成误解或超出实际能力 | 对外只描述已验收的接口、版本和平台；兼容性清单与测试报告一致 |

**法律风险可能影响构建方式和发布形态，而不只是增加一次审查。** 授权头文件、LGPL 再链接义务和专利覆盖应在开发第 1 周与架构评审同步处理。

### 6.5 商业承诺风险

源码级兼容产品应把承诺限定为：**指定应用、指定版本、指定接口清单、指定平台和指定测试场景。**

如果销售口径先表述为“CUDA 软件都能跑”，实际支持范围会无法控制，研发周期、测试责任和售后成本也随之失真。管理层在选路线时应同步批准对外兼容声明，而不只是批准技术架构。

## 七、实施路径与资源需求

### 7.1 排期口径与阶段划分

- 以项目启动为 W1，按自然周排期；每周一次里程碑检查，每两周一次管理层同步。
- **一期：功能兼容验收。** 覆盖第 3.1 节统一业务范围，形成可复现的像素、稳定性、资源与性能基线验收包。
- **二期：真实业务与生产交付验收。** 覆盖客户应用重编译/联调、自研平台全量回归、性能优化、部署、异常恢复和回退。
- 表中“标准排期”按人员到位、范围冻结、目标平台可用估算；“上限”含缓冲，不含范围变更。
- VAAPI 主线：一期目标 8 周、上限 10 周（含 2 周缓冲）；二期 4～6 周。总周期 12～16 周；二期与一期后段并行可压缩到 12～14 周。
- Vulkan Video 若正式支持：一期目标 10 周、上限 12 周，并另增双后端回归资源；Mesa 新增 frontends 适配不在本排期内，需单独立项，按 6～12 个月另行细化。
- 一期压缩的前提是：范围冻结、Gate G1/G2 按计划通过、目标平台无驱动阻塞、测试自动化可用。任一前提不成立，回到 10 周上限，不从稳定性和像素验证中挤时间。

### 7.2 一期排期（功能兼容验收）

**目标 8 周；W9～W10 为缓冲。若 Gate G2 在 W3 未通过或平台出现阻塞，按 10 周上限执行。**

| 周次 | 工作流 | 主要工作 | 交付物 / 出口 |
|---|---|---|---|
| W1 | 启动与冻结 | 冻结范围、接口、版本和验收标准；确认客户源码与构建条件；启动法务与平台基线 | 范围基线 v1.0；客户确认；法务问题清单 |
| W1～W2 | 平台 Gate G1 | 在自研平台验证 VAAPI/HIP、线性 surface、dma-buf、4K 和 8 路底层能力；归档 AMD 原始证据 | G1 通过，或触发降级方案 |
| W1～W2 | 构建与证据基线 | 重建 shim；锁定 FFmpeg/Mesa/ROCm/头文件版本；接通 FFmpeg 双路径冒烟；归档命令、日志和校验值 | 可复现构建包；证据包 v1.0 |
| W2～W4 | 解码主线 | 完成 CUVID 解码、映射、释放和错误处理；接通 `h264_cuvid` 与 `h264_nvdec` | 两条路径基础像素、帧数、顺序和生命周期通过 |
| W2～W3 | NPP 可行性 Gate G2 | 扩展参考矩阵（CUBIC/LINEAR/NN、1080p/4K、ROI、pitch）；完成 CUBIC 逐字节 spike | G2 结论：逐字节可行 / 需容差 / 需替代方案 |
| W3～W5 | NPP 实现 | 实现 3 个函数及必要 nppc/NPP SONAME；单函数与 NVIDIA 参考对照 | 单函数单测通过；NPP 库可被 FFmpeg 链接 |
| W4～W5 | 联合链路 | 解码 NV12 → NPP 缩放/转色 → HIP 读；验证零拷贝路径 | 联合链路逐平面正确 |
| W5～W7 | 复杂场景 | 裁剪、seek/flush、动态分辨率（按冻结范围）、长期参考、1080p/4K、1/8 路 | 场景矩阵通过，缺陷收敛 |
| W6～W8 | 稳定性与性能基线 | 1/8 路各 30 分钟；fd、显存、线程和资源检查；记录吞吐、p50/p95/p99、CPU 和显存 | 稳定性报告；性能基线报告 |
| W8 | 一期收口 Gate G3 | 全量回归、缺陷清零或书面豁免、证据归档、一期评审 | G3：一期通过，进入二期 |
| W9～W10 | 缓冲 | 仅用于吸收 G1～G3 的延期，不默认纳入交付承诺 | 缓冲消耗需管理层知悉 |

**一期出口（G3）至少满足：**

1. `h264_cuvid` 与 `h264_nvdec` 两条路径基础像素、帧数、显示顺序和资源生命周期通过。
2. 3 个 NPP 函数单测通过；联合链路逐平面结果正确；NPP 验收口径按第 8.1 节执行。
3. 冻结范围内的复杂场景、1080p/4K、1/8 路通过。
4. 1/8 路各 30 分钟无崩溃、死锁、非法访问或持续资源增长。
5. 性能基线、原始日志、参考结果和构建配置可复现。
6. 头文件、LGPL 和发布方式的法务路径可继续。

### 7.3 二期排期（真实业务与生产交付验收）

**标准 4～6 周；客户环境预准备从 W5 起并行，不占关键路径。若一期 W9～W10 缓冲被启用，二期整体顺延，客户环境预准备不受影响。**

| 周次 | 工作流 | 主要工作 | 交付物 / 出口 |
|---|---|---|---|
| W5～W8 | 客户环境预准备（并行） | 梳理客户源码、构建脚本、依赖和加载路径；提前暴露构建与版本问题 | 客户构建预检报告 |
| W9～W10 | 客户构建与联调 | 客户应用重编译/链接、版本检查、加载路径和依赖适配 | 客户构建通过 |
| W9～W12 | 自研平台全量回归 | 2 套自研平台；像素、帧序、资源、场景、8 路和 30 分钟；与 AMD 结果对照 | 平台回归报告 |
| W11～W13 | 性能优化 | 总吞吐、单路延迟、p50/p95/p99、CPU/显存、零拷贝收益和瓶颈定位 | 达标，或形成书面偏差与改进计划 |
| W12～W14 | 发布准备 Gate G4 | 部署、异常恢复、升级/回退演练、日志、法务、客户文档和培训 | G4：生产发布验收 |

> 客户与平台准备充分时，二期可按 4 周（W9～W12）执行；G4 前至少保留 1 周发布缓冲。若一期缓冲启用，二期整体顺延 2 周。

**二期出口（G4）至少满足：**

1. 客户应用在约定版本、构建配置和平台上完成业务回归。
2. 自研平台全量通过，不以 AMD 验证机结果替代。
3. 性能达到产品与客户共同确认的门槛，或有书面偏差结论。
4. 异常恢复、升级和回退演练通过，保留上一已验证版本。
5. 发布物、许可证、对应源码/再链接材料、兼容声明和客户文档齐备。

### 7.4 关键路径、并行关系与缓冲

- **关键路径**：平台 Gate G1 → 解码主线 → 联合链路 → 复杂场景 → 稳定性与性能 → 一期 G3 → 客户构建 → 平台全量回归 → 发布 G4。
- **可并行项**：NPP 可行性从 W2 启动；法务从 W1 启动；客户环境预准备从 W5 启动；证据归档贯穿全程。
- **缓冲**：一期 W9～W10 为 2 周缓冲；二期在 G4 前保留 1 周发布缓冲。缓冲不默认计入对外承诺。
- **Vulkan Video**：若纳入正式支持，一期增加 2 周；若与 VAAPI 并行，必须另增双后端回归资源，不能沿用单后端测试配置。
- **Mesa 新增 frontends 适配**：不纳入本排期；先完成接口和上游/分支策略设计，再按 6～12 个月单独立项。

### 7.7 排期前提与变更规则

- 增加编解码格式、图像处理函数、应用或客户；
- 改为通用二进制兼容或承诺任意 FFmpeg 版本；
- 正式支持 Vulkan Video 双后端，或启动 Mesa 新增 frontends 适配；
- 扩大动态分辨率、长期参考、多流或 8 路范围；
- 目标平台底层能力未通过 Gate G1，需要驱动协同或后端降级。

范围增加时只能调整范围、资源或周期，**不得从像素、稳定性或法律审查中压缩时间**。所有 Gate 结论、缓冲消耗和范围变更应形成书面记录，作为管理层继续投入或调整承诺的依据。

## 八、验收与发布要求

### 8.1 必须验证业务结果

| 层级 | 通过标准 | 不能替代该标准的证据 |
|---|---|---|
| 接口与加载 | 约定接口可调用，参数、回调、版本和错误行为符合范围 | 只有同名符号、库能打开 |
| 解码 | 帧数、显示顺序、真实像素和资源生命周期正确 | 会话创建成功、进程返回 0 |
| 显存直通 | HIP 能直接读取正确画面，声明零拷贝的路径无 CPU 中转 | 句柄导出或映射成功 |
| 图像处理 | 与约定参考结果一致；当前 NPP 范围为逐字节一致 | 视觉效果接近 |
| 场景覆盖 | 裁剪、跳转/清空、动态分辨率、长期参考和规定分辨率通过 | 单一正常码流通过 |
| 稳定性 | 1/8 路各 30 分钟，无崩溃、死锁、非法访问或持续资源增长 | 单次 30 帧运行成功 |
| 性能 | 吞吐、p50/p95/p99 延迟、CPU、显存和资源占用满足业务门槛 | 纯硬件解码 fps 或单次最优值 |
| 目标平台 | 实际自研硬件、驱动和软件栈全量通过 | AMD 验证机结果 |

一期可只建立性能基线；进入二期前，产品和客户必须确定总吞吐、单路延迟和资源门槛。

### 8.2 发布准入

1. 只发布已通过测试的应用、接口、格式和平台组合，未支持能力明确报错。
2. 保存版本、构建配置、输入、参考结果和原始日志，确保结果可复现。
3. 安装路径和加载路径明确，不未经验证覆盖系统或 NVIDIA 库。
4. 日志能区分加载、解码、映射、计算和同步故障，默认不记录原始视频。
5. 完成异常恢复、升级和回退演练，保留上一已验证版本。
6. 法务确认授权头文件、开源许可、专利覆盖和对外兼容表述。
7. 实验性后端与正式支持后端分开列示，防止客户把“代码存在”理解为“产品支持”。
8. 客户使用文档明确说明需要重新编译，不使用“原程序无需任何处理”等二进制兼容表述。

## 九、当前兼容路线的局限与自有 SDK 长期规划

### 9.1 当前源码兼容路线的长期劣势

无论选择 VAAPI、Vulkan Video 还是 Mesa 新增 frontends 适配，兼容层的本质仍是“接住别人的接口”。它能够解决近期迁移，但存在以下结构性局限：

1. **接口方向受制于外部生态。** CUDA、FFmpeg 和客户依赖发生变化时，我们需要被动跟随，难以完全控制版本节奏。
2. **每接一个客户都可能扩大范围。** 不同应用使用不同函数、格式和边界行为，有限兼容容易演变为持续定制。
3. **兼容保真与性能优化存在牵制。** 为匹配既有行为，需要保留特定错误处理、同步和资源生命周期，不一定始终是最适合自研硬件的实现。
4. **问题定位链路较长。** 故障可能位于客户调用、转接层、解析器、视频驱动或 HIP，现场诊断和售后成本较高。
5. **法律与依赖工作长期存在。** 专有头文件、FFmpeg 内部对象和兼容宣传需要随版本持续管理。
6. **难以形成完整的自主开发生态。** 只有兼容库，没有统一原生接口、工具、文档和示例，新客户仍可能围绕旧 CUDA 方式开发。
7. **兼容成果不一定形成产品差异化。** 客户感知的是“原来能跑的现在也能跑”，而不是自研平台自身更高效率和更易用的新能力。

因此，**兼容层适合作为存量业务迁移的桥梁，不应成为自研平台唯一的长期软件战略。**

### 9.2 为什么长期需要自有 SDK

自有 SDK 的目标不是再做一套庞大而封闭的接口，而是把已经验证的硬件能力沉淀为公司可控制、可演进、可支持的产品：

- 提供清晰的视频解码、图像处理、内存和同步接口；
- 为 FFmpeg、GStreamer 等常见框架提供原生接入；
- 建立示例、诊断、性能分析、版本政策和自动回归；
- 让新业务直接发挥自研硬件优势，而不必先模拟 CUDA 行为；
- 逐步减少专有头文件和外部接口变化对产品的约束；
- 将项目经验从“每个客户适配一次”转化为“多个客户复用一套能力”。

### 9.3 兼容层与自有 SDK 的关系

两者服务不同阶段：

| 阶段 | 主要目标 | 兼容层的作用 | 自有 SDK 的作用 |
|---|---|---|---|
| 当前：存量客户导入 | 降低迁移门槛，尽快形成可验收业务 | 保留主要 CUDA 调用，承接已有应用 | 复用其底层能力，不强制客户立即迁移 |
| 中期：能力产品化 | 减少重复定制，建立原生开发方式 | 维护已承诺客户和接口 | 提供原生视频、图像、内存和同步组件 |
| 长期：自主生态 | 提升新应用开发效率和平台差异化 | 作为旧应用支持或迁移工具，按生命周期维护 | 成为新应用默认开发入口 |

### 9.4 建议的长期演进路径

| 步骤 | 主要工作 | 与当前项目的衔接 |
|---|---|---|
| 1. 先完成有限兼容交付 | 选定一种源码兼容实现方案，完成当前 H.264 + 图像处理链路 | 解决存量客户导入，不等待完整 SDK 建成 |
| 2. 沉淀可复用原生组件 | 将解码会话、显存共享、图像处理、同步和诊断整理为内部稳定模块 | 避免兼容层与 SDK 各写一套底层实现 |
| 3. 建立原生开发入口 | 提供公开接口、FFmpeg/GStreamer 接入、示例和迁移指南 | 新业务优先使用自有 SDK，老业务继续使用兼容层 |
| 4. 建立版本与工具体系 | 完成兼容矩阵、诊断、性能分析、自动回归和发布政策 | 把项目制适配转为可持续产品维护 |
| 5. 分阶段迁移客户 | 按业务收益将适合的应用迁往自有 SDK | 兼容层逐步转为存量维护，而非无限扩张 |

自有 SDK 应作为**独立长期项目**立项，不纳入当前三种源码兼容方案的实施周期。启动时机应结合客户数量、重复适配成本、原生业务需求和团队承载能力决定。

### 9.5 长期投入的决策原则

- 当前兼容项目优先复用成熟组件，不为尚未确定的 SDK 设计过度扩张。
- 但核心模块应保持边界清晰，避免未来只能推倒重写。
- 当新增客户反复要求不同接口、维护成本持续增长，或新业务明确要求原生能力时，应启动自有 SDK 产品化。
- 对外应明确“兼容层负责迁移存量，自有 SDK 负责发展新业务”，避免两套路线争夺同一批需求而没有分工。

## 十、结论与待决策事项

### 10.1 兼容方式选择结论

| 兼容方式 | 结论 | 主要理由 |
|---|---|---|
| **二进制直接兼容** | **本期放弃，不纳入交付承诺** | 实现、测试、法律和维护成本较高；当前没有必须支持任意旧二进制的业务前提 |
| **源码级重编译兼容** | **本期采用** | 可复用现有成果，范围与版本可锁定，能以较少客户代码改动完成近期迁移 |

源码重编译兼容的成立前提是客户能够提供源码、构建环境和回归条件。无源码的重点客户如需支持，应单独重审二进制兼容。

### 10.2 源码兼容技术方案结论

| 技术方案 | 最核心的优点 | 最核心的缺点 | 更适合的决策取向 |
|---|---|---|---|
| **VAAPI 转接** | 底层证据较完整，线性显存直通，周期相对可估 | 主要面向 Linux，需要持续接口、依赖和法律维护 | 看重 Linux 近期交付，希望减少额外数据转换 |
| **Vulkan Video 转接** | 开放且具备跨平台潜力，已有实现基础 | 多一次显卡内转换，当前覆盖和性能证据较少，平台矩阵更复杂 | 看重跨平台和长期开放性，愿意承担额外验证与转换成本 |
| **Mesa 新增 frontends 适配** | 驱动行为控制力强，可能形成平台级长期能力 | 周期、驱动人才和长期维护投入高，不能自动解决 NPP 与客户计算代码 | 将兼容作为驱动战略，有稳定团队并可服务多个产品或客户 |

#### 关于 Mesa 新增 frontends 适配的结论

**本期可以排除 Mesa 新增 frontends 适配，不纳入候选方案、实施排期和交付承诺。** 主要理由：

1. **缺少同口径实现证据。** 该方案尚无与 VAAPI/Vulkan 相同业务范围的解码、显存共享和像素验收结果，当前无法按同一验收标准比较。
2. **周期与近期导入目标不匹配。** 粗估 6～12 个月，明显长于两种转接方案的一期周期。
3. **需要长期驱动团队和 Mesa 维护能力。** 无论进入上游还是维护私有分支，都需要持续的驱动开发、回归和多版本适配，属于长期平台投入。
4. **不能自动解决 NPP 和客户计算代码。** 图像处理、HIP 联合链路和 HIPIFY 仍需独立投入，排除视频解码入口本身的差异后，剩余工作量并不比转接方案少。
5. **测试和责任边界扩大到驱动层。** 需要承担驱动回归、多版本兼容和发布责任，不适合作为一期快速导入方案。

因此，本方案更适合作为长期驱动战略选项：若未来跨平台或平台级驱动能力成为明确业务需求，并具备稳定驱动团队和上游/分支策略，再单独立项评估。

**VAAPI 转接与 Vulkan Video 转接仍需管理层结合首批客户平台、跨平台订单、性能结果和团队能力作出选择。**

### 10.3 自有 SDK 长期结论

自有 SDK 是解决长期平台自主和生态建设的必要工作，应另行立项，不纳入当前源码兼容项目的实施周期。

- 当前兼容层负责承接存量 CUDA 业务；
- 自有 SDK 负责原生能力产品化和新业务发展；
- 中长期通过复用底层组件和分阶段迁移，使兼容层逐步转为存量维护。

### 10.4 管理层最终需批准的事项

| 待决策项 | 需要形成的明确结论 |
|---|---|
| 兼容方式 | 确认本期采用源码重编译兼容、不承诺二进制直接兼容 |
| 客户前提 | 首批客户是否均能提供源码、构建环境和业务回归条件 |
| 技术方案 | 选择 VAAPI、Vulkan Video、Mesa 新增 frontends 适配，或有额外资源保障的组合方案 |
| 业务边界 | 首批客户、宿主、格式、接口、平台和生产场景 |
| 时间与资源 | 批准所选方案对应的周期、核心团队、测试人员和持续维护预算 |
| 跨平台策略 | 跨平台是已有业务需求还是未来选项，决定 Vulkan Video 的战略权重 |
| 法律路径 | NPP 头文件、FFmpeg LGPL、专利、商标及兼容声明的审查结论 |
| 客户责任 | 重编译、业务测试和迁移工作由哪一方承担 |

## 十一、附录

### 11.1 简明术语

| 术语 | 业务含义 |
|---|---|
| CUDA | NVIDIA 的软件开发和运行平台 |
| NVDEC / CUVID | NVIDIA 的硬件视频解码能力及调用接口 |
| NPP | NVIDIA 的图像处理库，本比较只覆盖实际使用的 3 个函数 |
| VAAPI | Linux 通用的视频硬件加速接口 |
| Vulkan Video | 开放标准的视频编解码接口，具备跨平台潜力 |
| HIP / ROCm | AMD 生态的计算接口和运行平台 |
| 转接库 / shim | 保留 NVIDIA 调用方式、内部改用其他实现的中间软件 |
| 源码级兼容 | 保留主要调用方式，但需要客户重新编译和验收 |
| 二进制兼容 | 客户原程序不重编译，直接加载兼容实现 |
| SONAME / ABI | 库加载名称及二进制层面的函数、结构和调用约定 |
| 显存共享 / 零拷贝 | 解码与计算使用同一份显存数据，不经过 CPU 中转 |
| 线性 / 分块画面 | 前者可按普通内存顺序读取；后者需转换后才能由 HIP 普通指针直读 |
| 主机同步 | 由 CPU 控制解码、计算和资源回收的先后顺序 |
| HIPIFY | 将客户自有 CUDA 源码转换为 HIP 源码的工具，不能翻译 NVIDIA 闭源库 |
| 一期 / 二期 | 功能兼容验收 / 真实业务与生产交付验收 |

### 11.2 验证环境

| 环境 | 硬件 | 用途与边界 |
|---|---|---|
| AMD 验证机 | Radeon RX 7900 XTX | 解码、显存共享、同步、真实像素和 Vulkan 备选验证 |
| 历史格式对比机 | AMD RX 9070 + NVIDIA RTX 4060 | 15 组格式能力对比，仅作路线参考 |
| NVIDIA 参考机 | GeForce RTX 4060 | NPP 11.5.1.107 基准输出 |
| 自研目标平台 | 待项目启动时锁定 | 最终交付验收，不能由 AMD 结果替代 |
